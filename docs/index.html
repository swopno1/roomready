1. Product definition

1.1 One line

RoomReady is the offline-first housekeeping companion for resorts running ViveReply Suite: room turnover, checklists and maintenance tickets that work with zero internet.

1.2 The problem

Resort staff work where the wifi doesn't reach — hillside villas, basements, remote properties. Housekeeping runs on radios, paper and memory. When the network drops, the front desk loses sight of which rooms are actually ready, and a guest is walked to a dirty room. RoomReady exists so the work never stops when the network does, and so the Suite always knows the true state of every room.

1.3 Users

User What they do in RoomReady
Housekeeping staff Tick turnover checklists, update room status, raise tickets, add room notes
Housekeeping supervisor Assign rooms, inspect and sign off, re-open failed inspections
Maintenance staff Pick up tickets, update progress, mark resolved with photo proof
Front desk / manager Read-only board of room readiness, block check-in until Ready/Inspected
Resort owner Reports: turnover time, rooms per staff per day, ticket SLA, property health

1.4 The offline promise (non-negotiable)

  1. The app opens and works with airplane mode on — first load caches everything, later loads need no network at all.
  2. Every action a staff member takes offline is stored on-device and synced when connectivity returns. No work is ever lost to a dead zone.
  3. The demo video proves it: the airplane-mode test is the product's core claim, and every release must pass it before shipping.

1.5 Non-goals

  • RoomReady is not a booking engine, a PMS, or a guest-facing app. The Suite owns reservations, rates, payments and guest data.
  • RoomReady stores no guest personal data by design (see §8.4). Rooms are identified by unit; bookings are referenced by ID only.
  • No real-time chat, no guest messaging, no OTA sync. Those belong to the Suite roadmap, not this product.

2. Platforms

One codebase, two surfaces. The PWA is the product; Android is the same product in a store shell.

2.1 PWA (web) — the primary surface, already built (Hackyard MVP)

  • Vanilla HTML/CSS/JS, zero dependencies, zero network calls.
  • Service worker (cache-first app shell), localStorage in the MVP, installable via Web App Manifest.
  • Runs on any modern browser; installable on Android and desktop from the browser. This is the surface staff use on shared tablets and phones.

2.2 Android app — Capacitor wrapper (recommended)

Recommendation: Capacitor (capacitorjs.com) wrapping the existing PWA codebase. One codebase, one release train, native capabilities where the browser can't reach.

Why Capacitor over the alternatives:

Option Verdict
Capacitor (recommended) Wraps the existing PWA as-is. Native plugins for SQLite (encrypted on-device DB), camera, push (FCM), background sync, secure storage. Play Store presence with a real APK/AAB. Smallest rewrite: the PWA stays the PWA.
Trusted Web Activity (TWA) Lighter — the Play listing is essentially the PWA. But no SQLite, no background sync, no camera beyond the browser, and the Play experience is thinner. Fallback if Capacitor proves too heavy.
React Native / Flutter rewrite Full native power, but a complete rewrite of a working product for no user-visible gain at this stage. Revisit only if the product outgrows the web model.

Founder decision (see §13): confirm Capacitor as the Android path, or choose TWA as the lighter first step.

2.3 Platform principles

  • Offline-first on both surfaces. The Android app must pass the same airplane-mode test as the PWA.
  • One data model, one sync engine. Web and Android share the store and the sync protocol (§3.3). A fix in one ships in both.
  • No platform-only features in Phase 2. Anything built for Android (photo evidence, push) must degrade gracefully on the PWA, not fork it.

3.2 Local store — migration path

Stage Store Notes
MVP (now) localStorage, key roomready.v1 Simple, reliable, enough for 21 rooms. Single JSON blob.
Phase 2 IndexedDB via Dexie (or localForage) Per-record storage, queries, larger data, proper indexes. Migration: one-time import of the localStorage blob on first Phase-2 launch.

Schema (core tables, all records carry property_id, updated_at, updated_by, deleted_at for soft delete):

  • rooms — id, property_id, unit_id (Suite), name, type, status, assignee, note
  • checklist_items — id, room_id, template_item_id, done, done_by, done_at
  • checklist_templates — id, property_id, room_type, items[]
  • tickets — id, property_id, room_id, title, priority, status, created_by, assigned_to, photo_urls[], resolved_at
  • status_log — id, room_id, from_status, to_status, by, at, device_id
  • sync_outbox — id, operation, payload, idempotency_key, attempts, status

3.3 Sync engine

  • Outbox pattern. Every mutation writes locally first, then appends an outbox entry. The engine replays the outbox when online, oldest first.
  • Idempotency keys. Every outbox entry carries a UUID. Replays are safe: the server ignores duplicates.
  • Conflict rules (server is the arbiter, but merges where safe):
  • Checklist items: union merge — a tick on either side wins.
  • Room status: last-write-wins by server timestamp.
  • Tickets: server wins on status transitions; client wins on new tickets.
  • Notes: last-write-wins, with both versions kept in the status log.
  • Background sync. Web: Background Sync API where available, plus retry on app foreground. Android: WorkManager periodic sync + immediate sync on connectivity change.
  • Sync health. The app shows pending-change count; the Suite dashboard shows per-device last-sync time and failed-operation alerts.

3.4 API style

  • REST, JSON, versioned (/api/v1/...). Pagination (cursor-based) on all list endpoints. Rate limits per property and per device.
  • All mutations are authenticated (§7) and validated at the boundary (Zod schemas on the API, Prisma parameterized queries underneath).
  • No guest PII crosses this API (see §1.5, §8.4).

4. Wiring with ViveReply Suite

RoomReady is a Suite module first, a standalone product second. The Suite is the source of truth; RoomReady is the offline edge that feeds it.

4.1 Source of truth

Data Owner RoomReady's role
Properties, room units, room types Suite Read-only import. RoomReady never invents rooms.
Reservations, check-in/out Suite Drives turnover (§4.2). RoomReady never creates bookings.
Staff, roles, assignments Suite Read-only import + role mapping (§7.3).
Housekeeping status, checklists, tickets Shared RoomReady writes offline; Suite stores and serves the canonical state.
Audit log Suite Every status change lands here, with who/when/device.

4.2 The turnover loop (the core integration)

  1. Guest checks out (Suite) → Suite creates a turnover job: room → Dirty, checklist reset, assigned to on-duty housekeeping.
  2. Staff open RoomReady (offline, on the floor) → see the room as Dirty → tick the checklist → status advances Dirty → Cleaning → Inspected.
  3. Supervisor inspects and signs off → status Ready.
  4. Suite releases the room for the next check-in. Check-in is blocked until the room is Ready or Inspected — the Suite enforces this, so a guest is never walked to a dirty room.
  5. If inspection fails → room back to Dirty with a note; the loop repeats.
  6. Maintenance issues found mid-turnover become tickets (§5), linked to the room and visible to the front desk.

4.5 Deployment topology (two phases)

  • Phase A — embedded module (first). RoomReady ships inside the Suite deployment as a /housekeeping route of the same Next.js app. Same origin: no CORS, shared session cookie, shared auth, one deploy. This is the fastest path to a pilot property.
  • Phase B — standalone (later). RoomReady PWA + Android point at the Suite API from their own origin. Needs CORS allowlist, token auth (Authorization Code + PKCE for Android, §7.1), and a public API stability commitment. Only after Phase A proves the sync engine in production.

4.6 Migration path from the Hackyard MVP

  1. Property setup wizard (Suite admin): pick property → import room units → import staff → pick checklist templates → assign on-duty staff.
  2. MVP localStorage seed data is demo-only and is wiped on first Suite import. No demo data ever ships to a real property.
  3. The MVP's offline engine (service worker + outbox) carries over unchanged; only the store backend changes (§3.2).

6. Android app plan (Capacitor)

6.4 Offline on Android

  • Same airplane-mode test as the PWA, run on a real device before every release. SQLite holds the store; WorkManager replays the outbox.

7. Authentication & authorization (with ViveReply Suite)

RoomReady does not run its own identity system. The Suite is the identity provider; RoomReady is a client of it.

7.1 Authentication (how staff sign in)

Surface Mechanism
Embedded module (Phase A) Shared Suite session cookie (httpOnly, Secure, SameSite=Lax). No separate login. Staff sign in to the Suite once.
Standalone PWA (Phase B) OAuth 2.0 Authorization Code + PKCE against the Suite, tokens in memory + httpOnly refresh cookie. No tokens in localStorage.
Android app (Phase B) Same OAuth + PKCE flow via Custom Tabs; tokens in EncryptedSharedPreferences / Android Keystore.

Token policy:

  • Access token: 15 minutes, JWT, scoped to one property + role.
  • Refresh token: 7 days, rotating on each use, revocable server-side. Re-use of a refresh token revokes the whole token family (theft detection).
  • Absolute session limit: 30 days, then full re-authentication.
  • Offline grace: a cached session lets the app keep working offline for up to 7 days; on reconnect the token is refreshed silently. Past 7 days offline, the app requires re-authentication before syncing (local data stays readable, new syncs are blocked until auth succeeds).

7.2 Device trust

  • Each device gets a device_id on first login (stored server-side per user).
  • Owners/managers can list and revoke devices from Suite admin.
  • A revoked device stops syncing immediately; its local data is wiped on next launch (or next sync attempt, whichever comes first).
  • Lost/stolen device procedure: revoke from Suite admin → tokens dead → local data unreadable without the app's encrypted store (§8.3).

7.3 Authorization — role matrix

Roles come from the Suite (verified: Owner, Manager, Front Desk, Housekeeping, Kitchen, Storekeeper, Accountant, HR, Auditor). RoomReady uses the subset below; unlisted roles have no access to RoomReady.

  • Other roles: 2FA optional, recommended for supervisors.
  • 2FA is enforced at Suite login; RoomReady inherits it (no separate 2FA).

8. Security — standards, measurements, policy

8.1 Standards (what we build to)

  • OWASP ASVS Level 2 as the baseline for the API and the app. (ASVS L1 for the MVP; L2 before a paying property goes live.)
  • OWASP Top 10 (2021) — addressed explicitly in code review checklists.
  • TLS 1.2+ (1.3 preferred) everywhere; HSTS (max-age=31536000, includeSubDomains, preload when stable).
  • Content Security Policy: strict CSP on the PWA shell (no inline scripts in the production build; nonces where needed). No unsafe-inline, no unsafe-eval.
  • Headers: X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN (or frame-ancestors 'self'), Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy (camera/microphone/geolocation off except where the app needs them, and only on the app's own origin).
  • CSRF: SameSite=Lax cookies + anti-CSRF tokens on all mutations when cookie auth is used. Token auth (Phase B) uses Authorization: Bearer with no ambient credentials.
  • Input validation: Zod schemas on every API boundary; Prisma parameterized queries underneath (no raw SQL with interpolation).
  • Secrets: environment variables / Vercel env only. Never in the repo, never in the client bundle, never in logs. .env.example carries placeholders only.
  • Dependencies: Dependabot on; npm audit in CI, failing the build on any critical finding and on high findings older than 14 days.
  • Rate limiting: login (5 attempts / 15 min / IP + account lockout after 10), sync endpoint (per device, burst-tolerant), public routes.
  • Audit logging: every auth event, role change, status change, ticket transition and device revoke — who, when, device, property, IP (hashed after 30 days).

Full runbook lives in docs/security/runbook.md (to be written in Phase 2).

8.3 On-device / offline security

  • Android: SQLite encrypted with SQLCipher; tokens in EncryptedSharedPreferences (Keystore-backed); photos in app-private storage (not shared media folders).
  • Web: data lives in the browser profile (IndexedDB). Accept the browser's profile encryption; warn on shared devices (a "shared device" mode that wipes local data on logout).
  • No secrets on device: API keys and service credentials never ship in the client. The client holds only the user's own tokens.
  • Remote wipe: revoke device (§7.2) → tokens dead, local store wiped on next launch.

8.4 Data protection & privacy (by design)

  • Minimisation: RoomReady stores staff identity (name, role), room state, checklists, tickets, photos of rooms. It stores no guest names, no guest contact details, no payment data. Bookings are referenced by ID only; if a UI ever needs a guest name, it fetches it live from the Suite and never persists it on-device.
  • Encryption: in transit (TLS), at rest (Suite DB encryption, Android SQLCipher).
  • Retention: housekeeping logs 12 months, then anonymised (staff IDs hashed) and archived; tickets with photos 24 months; audit log 24 months. (Founder to confirm — see §13.)
  • Access: staff see only their own property (§7.3). Cross-property access needs an explicit owner grant.
  • Backups: Suite DB point-in-time recovery; RoomReady has no separate backup (its data lives in the Suite DB once synced; unsynced on-device data is the device's responsibility until sync).

8.5 Compliance notes (not legal advice)

  • GDPR (EU guests/properties): RoomReady is a processor of staff data and room-state data on behalf of the resort (controller). Needs a DPA (§9). Guest data is not processed by RoomReady by design.
  • Bangladesh: no comprehensive data-protection law in force at the time of writing; follow GDPR-level practice anyway (it is the stricter bar and the one EU-facing properties will ask about).
  • Children's data: none collected. Staff must be 18+ per the resort's employment.
  • Founder to confirm with counsel before the first paying property.

10.2 Hosting & CI/CD

  • Caching rules: app shell + static assets immutable (max-age=1y, content-hashed); API responses no-store; service-worker updates prompt the user (never a forced reload mid-shift).

10.3 Monitoring & reliability

  • Errors: Sentry (client + API), with PII scrubbing on. Alert on error spikes and on sync-failure rate > 1%.
  • Uptime: external check on the PWA shell + API health endpoint; status page for properties.
  • Sync observability: per-property pending-outbox age, failed-operation counts, last-sync per device — visible on the Suite dashboard.
  • Logging: structured logs, no PII, 30-day retention.
  • Backups: Suite DB point-in-time recovery (tested quarterly, §8.2).
  • Rollback: Vercel instant rollback for the shell; Play staged-halt for Android; API deploys are backwards-compatible for two versions (version skew policy, §6.5).

Appendix A — Glossary

Term Meaning
PWA Progressive Web App — a website that installs like an app and works offline
TWA Trusted Web Activity — a Play Store wrapper that is essentially the PWA
Capacitor A runtime that wraps a web app as a native Android/iOS app with plugin access
Outbox The on-device queue of changes waiting to sync
Idempotency key A UUID per change so a retried sync never applies twice
PITR Point-in-time recovery (database restore to any second)
FCM Firebase Cloud Messaging (push notifications on Android)
PKCE Proof Key for Code Exchange (OAuth security for public clients)
SQLCipher Encrypted SQLite
ASVS OWASP Application Security Verification Standard
DPA Data Processing Addendum
SLA Service-level agreement (here: ticket response/resolution targets)
